# FluffyMachines 26.2.15 — Backpack Transfer Lifecycle

Backpack Loader and Unloader now revalidate their machine and installed backpack after an asynchronous lookup, immediately before changing inventory contents. Work targeting a replaced backpack, removed or evicted menu, invalidated backpack instance, or insufficient energy is cancelled. The next valid operation can proceed normally.

The Loader repeats its input eligibility check before moving a stack, so an input changed to a backpack or shulker box during the lookup cannot bypass the nesting restriction. The Unloader retains its input when an empty backpack cannot fit into the output slots. Returned insertion remainders remain at the source, and an insertion that moves nothing does not consume energy.

Initial inventory inspection and backpack routing now use synchronized machine ticks. Final transfers continue to run on the server thread. Existing item IDs, backpack PDC and supported legacy owner/ID lore, item metadata, slot order, normal one-stack transfers and the 16-energy cost are preserved. Full/empty-backpack routing still costs no energy. There is no saved-data format migration.

## Compatibility and validation

Minecraft **1.21.11** and **Java 21 bytecode** remain the runtime floor, with the Java 25 build toolchain and retained 26.2/26.3 API checks. The 26.2 compile lane now pins `26.2.build.132-stable`: its former version range could resolve to a 26.3 prerelease and therefore did not reliably test 26.2.

Local full Maven verification of the candidate passed the 33 existing tests (20 barrel and 13 recipe-cache tests) on each of the three actual API lanes, using the checksum-verified published Slimefun Legacy 4.1.71 core. All tests passed with no skips, and compiler warning identities matched the baseline. All three builds contain identical archive entries, with Java 21 addon bytecode, valid archive checksums and no bundled core.

The [native regression helper](../../scripts/runtime/README.md) invokes the registered production machine tickers with the actual core/addon JARs in disposable Paper servers. It controls the existing profile callback executor to test delayed transfers and uses separate server processes for persistence checks. Its gate requires all 22 transfer cases and four restart controls on each pinned Paper runtime; incomplete reports and plugin failures cannot pass. Published Slimefun Legacy 4.1.71 is the runtime baseline, while the workflow also retains the current core source build for ordinary compile/API checks. Native reports and final-source CI results are recorded in the pull request before publication.

Build success and fixture tests do not certify every production-world interaction. Machine inventory writes and backpack persistence are not one atomic crash-recovery transaction, and this change does not add Folia support.
